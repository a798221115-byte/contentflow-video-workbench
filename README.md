# ContentFlow 视频号矩阵工作台

ContentFlow 是一个面向视频号矩阵的内容经营工作台，把下面这条完整链路放进同一个系统：

```text
来源与选题 → 文案确认 → 配音与分镜 → 成片交付 → 发布授权 → 数据快照 → 实验复盘
```

当前版本聚焦三个视频号的日常内容协作。对标账号采集、Firecrawl 和视频号助手自动同步将在后续版本逐步接入。

## 当前功能

- 三账号矩阵总览与账号筛选
- 账号作为父级节点的展开树，以及账号新增、编辑和安全删除
- 删除父级账号时先把全部子内容移交到另一个账号，避免资料丢失
- 总览生产阶段可点击进入对应阶段，顶部日期可进入当天任务
- 独立经营分析页：日/周/月趋势、环比、内容漏斗、账号健康度和复盘动作
- 首页对标雷达入口，并明确区分演示信号与真实采集数据
- 对齐 `produce-wechat-book-video-history v3.11.0` 的七阶段历史生产流水线
- 新建选题与高优先级标记
- 口播脚本、开场钩子及拍摄剪辑备注
- 内容阶段推进与计划发布时间
- 播放、点赞、评论、转发和涨粉数据回收
- 复盘结论与下一次验证动作
- D1/SQLite 持久化存储
- 链接原稿、结构拆解与原创二创资料卡
- 文字/链接双入口，以及“正常历史二创 / 成稿直出”两条分支
- G01 微信读书证据包、O01 文皮皮原创检测和 C01/C02 风险门禁
- 仅两次人工生产确认：G02 文案、G04 全部分镜图片
- 10 个长标题 + 10 个短标题 + 10 组发布话题自动选择与归档
- VoxCPM 历史学者型合成男声、真实配音时间轴和语义分镜
- G05 成片、独立 1080×1260 封面、G06 交付登记
- G07 草稿 / G08 授权发布边界，以及 24h、72h、7d 独立数据快照
- 本地开发与私有部署

## AI 视频生产链路

打开任意一条内容，会进入一张完整生产资料卡：

```text
文字/链接入口 → G01 证据包 → O01 原创检测 → G02 文案确认 → C01 → 标题话题 + V01 配音 → G03 样图 → G04 全图确认 → G05/C02/G06 → G07/G08 → G09
```

- `dbs-content` 只诊断参考稿机制；正常二创以微信读书核验材料与原创观察重建内容。
- 正常二创必须把完整参考稿与完整二创稿交给文皮皮检测，明确显示“鉴定结果：原创”后才开放 G02。
- “成稿直出”逐字保留用户成稿，跳过二创与 O01，并将明确指令视作第一次确认。
- 图片数量由真实配音时间轴和语义变化决定；约 8 秒一张只是节奏软检查，不再按视频分钟数硬算张数。
- 历史赛道默认 `history-scholar-male-locked-v1` 原创合成男声，不使用真实名人录音做克隆参考。
- 媒体文件存入 R2，结构化生产资料与指标存入 D1。
- VoxCPM、图片/动画生成、自动剪辑和截图 OCR 都采用可插拔服务；未连接时页面会明确显示待接入，并允许上传现有成品继续生产。

## 本地运行

需要 Node.js `>=22.13.0`。

```bash
npm install
npm run dev
```

开发服务启动后，打开终端显示的本地地址。通常是 `http://localhost:3000`；如果端口已占用，会自动使用下一个可用端口。

## 验证

```bash
npm test
```

这会执行完整构建，并检查七阶段工作流、持久化配置和产品元数据。

数据库结构变化后生成迁移：

```bash
npm run db:generate
```

## 版本管理

项目使用[语义化版本](https://semver.org/lang/zh-CN/)：

- `MAJOR`：不兼容的重大产品或数据结构变化
- `MINOR`：向后兼容的新功能
- `PATCH`：向后兼容的问题修复

当前版本：`v0.4.0`

版本发布流程：

1. 在功能分支完成修改。
2. 运行 `npm test`。
3. 更新 `CHANGELOG.md`。
4. 更新 `package.json` 中的版本号。
5. 合并到 `main`。
6. 创建与版本号一致的 Git 标签，例如 `v0.3.0`。
7. 推送分支与标签到 GitHub。

## 目录说明

- `app/`：页面、样式及工作台接口
- `db/`：数据结构和数据库访问
- `drizzle/`：数据库迁移
- `tests/`：MVP 完整性测试
- `public/`：分享预览等静态资源

## 数据安全

- 不要把视频号登录凭证、Cookie、API Key 或私密经营数据提交到 GitHub。
- `.env`、本地数据库状态和构建产物应保持在 `.gitignore` 中。
- GitHub 仓库建议保持为 Private。
